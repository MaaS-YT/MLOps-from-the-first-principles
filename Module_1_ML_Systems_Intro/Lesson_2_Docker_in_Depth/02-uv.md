## What `uv` Is

`uv` is a Python package and project manager written in Rust. It replaces:

- `pip` (install)
- `venv` (create environment)
- `pip-tools` (lock dependencies)
- `pipx` (run tools)
- `pyenv` (manage Python versions, optional)

It's fast — 10–100x faster than `pip` — because it caches aggressively and resolves in parallel.

But speed is not the point. **Reproducibility is the point.**

---

## The Two Files

`uv` manages two files:

**`pyproject.toml`** — what you *want*:

```toml
[project]
name = "iris-training"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = [
    "scikit-learn>=1.4",
    "joblib>=1.3",
]

[tool.uv]
package = false
```

**`uv.lock`** — what you *get*:

```toml
# Auto-generated. Do not edit by hand.
# Pins exact versions of every dependency AND every transitive dependency.
```

| File | Written by | Committed? | Purpose |
|------|-----------|------------|---------|
| `pyproject.toml` | You | Yes | Declare intent |
| `uv.lock` | `uv` | Yes | Pin reality |

The lockfile is the contract. Same lockfile → same environment, on any machine.

---

## The Commands That Matter

```bash
# Create .venv and install everything from pyproject.toml + uv.lock
uv sync

# Same, but fail if the lockfile is out of date with pyproject.toml
uv sync --frozen

# Add a dependency — updates pyproject.toml and uv.lock
uv add scikit-learn

# Run a command inside the venv without activating it
uv run python train.py

# Refresh the lockfile without installing
uv lock
```

That's 90% of day-to-day use.

---

## Why `--frozen` Matters

`uv sync` will happily update the lockfile if `pyproject.toml` has changed.

`uv sync --frozen` will **refuse** and exit non-zero.

Use `--frozen` in:

- CI pipelines
- Docker builds
- Production deploys

**Why:** you want "the environment I tested" to equal "the environment I'm shipping." Silent re-resolution breaks that guarantee.

## A Note on Workspaces

`uv` supports **workspaces** — multiple projects sharing a single lockfile at a repo root. DDODS is one: the root `pyproject.toml` declares shared dependencies, and `uv` resolves against it.

For this lesson, `training/` is a **standalone project**, not a workspace member. It has its own `pyproject.toml` and `uv.lock`. Commands run from inside `training/` operate only on this project.

If `uv lock` inside `training/` errors with a workspace message, the parent `pyproject.toml` has claimed `training/` as a member. Two ways to fix:

**Add it as an explicit member** in the parent `pyproject.toml`:

```toml
[tool.uv.workspace]
members = [
    "Module_1_ML_Systems_Intro/Lesson_2_Docker_in_Depth/training",
]
```

**Or exclude it**:

```toml
[tool.uv.workspace]
exclude = [
    "Module_1_ML_Systems_Intro/Lesson_2_Docker_in_Depth/training",
]
```

Either works. The lesson uses exclude so `training/` behaves as a standalone project — which is what step 05's Dockerfile expects.

## What This Buys You

Compare:

| Without `uv` | With `uv` |
|--------------|-----------|
| `python -m venv .venv && source .venv/bin/activate` | `uv sync` |
| `pip install -r requirements.txt` (slow, no lock) | (`uv sync` did it) |
| Manually pin transitive deps | `uv.lock` pins everything |
| "Works on my machine" | Lockfile travels with the repo |

Same idea as a venv. Better ergonomics. **The abstraction is unchanged: isolate packages, lock versions, reproduce anywhere.**

Remember this feeling. In step 04, containers do the same thing — one level up.

## Checkpoint

You should now be able to answer:

- **What are the two files?** `pyproject.toml` (intent) and `uv.lock` (reality).
- **Why commit both?** Declared intent + pinned reality = reproducible build.
- **Why `--frozen` in CI?** To fail loudly if the lockfile drifts, rather than silently re-resolving.
- **What's a workspace?** Multiple projects sharing one lockfile at a repo root. This lesson's `training/` opts out.
